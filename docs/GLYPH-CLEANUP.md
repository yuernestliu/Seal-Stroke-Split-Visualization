# 字形清理与接入 Notes

## 1. 目的

把原包笔段画成没有像素毛边的矢量线条。整字、拆笔、独立笔段必须使用同一组路径；不要在“合字”时换成另一套字体。

项目目录：`github-page/Seal-Stroke-Split-Visualization`。这是后续处理剩余字形的 agent 入口，不需要读取整段聊天。

## 3. 已确定的原则

- 原始 `data/glyphs.js`、原图、笔段 ID 和分段记录保持不变；新结果单独存放。
- 输入坐标是 `[y, x]`，SVG 坐标是 `x y`。保留原始画布尺寸与笔段端点。
- 先轻量平滑中心线，再简化为二次曲线路径，以圆角、圆端点绘制；当前四个字的笔宽是 3.2 原图像素单位。
- 合字和拆笔只改变颜色；独立笔段引用同一条 `d` 和 `stroke-width`，不再分别描边或生成另一份几何。
- 清理记录的 `display_checked` 只表示显示与对应关系检查通过，不表示文字学解释已核定。
- 其他 120 个字仍保留旧显示方式；不要盲目把全部自动结果发布。

## 5. 分工和操作步骤

每个 agent 只接自己分配的完整字形 ID，并只修改对应 JSON。不要同时改汇总 JS、主页面或通用算法，避免覆盖别人的结果。

1. 按 ID 查看 `data/glyphs.js` 中该字的画布、笔段坐标与原图。遵守全局 AGENTS.md；所有 `_FORBIDDEN_*` 路径及符号链接均不可作为输入。
2. 生成草稿，例如：

   ```bash
   python3 scripts/build_cleaned_glyphs.py generate --ids '分配到的完整字形ID'
   ```

   也可使用 `--marks 字1 字2`，但同字存在多个样本时必须用 ID。已有 JSON 会拒绝覆盖；需要修改时直接在该记录上修正并保留说明。

3. 检查草稿中的 `strokes`。`path` 使用 `M/L/Q`，`width` 为笔宽。需要逐字或逐笔修正时，修改自己的 JSON，记录调整理由；不要更改共享算法来迎合一个字。
4. 制作本字原图/合字/彩色拆笔对照。可复用 `preview_clean_strokes.py` 的 `svg()` 辅助函数，在 `public/proofs/` 输出独立的 `agent-<完整ID>.html`；不要覆盖四字参考页。
5. 视觉核对和下方验收通过后，把自己的记录 `status` 改为 `display_checked`，填写 `review`，说明检查项、日期和人工调整。
6. 将逐字 JSON 交给负责汇总的 agent；由汇总者执行：

   ```bash
   python3 scripts/build_cleaned_glyphs.py publish
   npm run check
   npm test
   ```

   `publish` 排除所有 `draft`，拒绝来源签名改变、画布/笔段 ID 不一致、端点改变、非法坐标及重复记录。

## 6. 不要重复做的事

- 不要只沿低分辨率原图轮廓描边：毛边会被一起矢量化。
- 不要默认大字用崇羲篆體、拆笔却用原包；已处理的字始终优先使用清理路径，即使字体后来加载成功。
- 不要把轮廓重合率当作单一通过门槛。均匀笔宽会改变像素面积；当前四字诊断约为 0.779–0.799，不代表字形结构自动正确。
- 不要重做故事、修改学术解释、重跑原分割工程或动官方字体。它们不是逐字清理任务的范围。
- 不要新增用户菜单、播放、描写或猜字按钮。当前页面保持“一键拆笔”。

## 7. 下一步与验收

按分配字形逐字处理，优先从少笔、分段清楚的样本开始。复杂或可疑样本保留 `draft` 并写清问题，不强行发布。

必须检查：笔段数量和 ID、端点、画布、交叉点、闭合圈、很短的笔画、有没有新连接或断裂。原分段本身可能有误；不应通过平滑掩盖问题。

接入后核对：默认整字与拆笔的 `d`、笔宽、端点样式相同；每个独立笔段对应同一条路径；字体加载后不会覆盖清理版；切换字会复位拆笔；字库、故事对照和关系节点没有显示另一套笔形。
